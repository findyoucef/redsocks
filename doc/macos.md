# macOS IPv4 TCP and UDP port

This port uses macOS PF to redirect IPv4 TCP connections to SOCKS4, SOCKS5,
or HTTP CONNECT proxies. IPv4 UDP uses SOCKS5 UDP ASSOCIATE: PF can redirect
traffic to one configured destination, while a utun interface handles arbitrary
destinations. The portable tests run without root or firewall changes. Live
interception tests additionally run on Intel and Apple Silicon macOS CI.

## Build and test

Install Apple's Command Line Tools and libevent:

```sh
xcode-select --install  # only if Command Line Tools are not already installed
brew install libevent pkgconf
make -j4 CC=clang
make check
./redsocks -t -c examples/redsocks-macos.conf
./redsocks -t -c examples/redsocks-macos-udp.conf
./redsocks -t -c examples/redsocks-macos-udp-fixed.conf
```

The Makefile discovers Homebrew's libevent prefix on Intel and Apple Silicon.
For a different installation, use `make LIBEVENT_PREFIX=/path/to/libevent`.
Run `make clean` when changing compiler, target, `DBG_BUILD`, `REDUDP`, or `DNSU2T`.
The optional `make install PREFIX=/usr/local` installs the binary in
`/usr/local/sbin`; it requires permission to write there.

`make check` covers HTTP CONNECT with CRLF responses, Basic authentication,
SOCKS5 binary forwarding, recovery after idle connections relieve connection
pressure, and failure to drop supplementary groups. The six UDP cases cover
binary and empty datagrams, separate clients, expired or disconnected
associations, authentication, wildcard relay addresses, and malformed replies.
These tests use local fake upstream proxies with `redirector = generic`;
they do **not** validate PF lookup, NAT, or utun packet delivery.
The legacy `make test` suite still requires Linux, Docker, pipework and Python 2.

## Start the TCP proxy

First arrange an upstream SOCKS5 proxy listening at `127.0.0.1:1080`, or edit
`ip`, `port`, `type` and credentials in `examples/redsocks-macos.conf`.
For HTTP CONNECT use `type = http-connect`. Then run:

```sh
sudo ./redsocks -c examples/redsocks-macos.conf
```

Start redsocks as root so it can open PF, listeners, and any utun interface.
The examples then set `user = "nobody"; group = "nobody";` to drop the
forwarding process's privileges. A small helper retains root solely for PF
original-destination lookups: the worker passes the accepted TCP socket, and
the helper derives the endpoints itself. It cannot accept firewall edits or
arbitrary ioctl commands. The worker closes its PF descriptor before dropping
privileges. Darwin checks the caller's UID on every PF ioctl, as shown in
[Apple's implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/net/pf_ioctl.c).

Use an account different from the application user being captured; a dedicated
service account is preferable when deploying several unrelated daemons. Keep
`daemon = off` for foreground use or launchd. Ctrl-C or SIGTERM stops the
worker and closes the helper channel. If the helper fails, PF lookups fail
closed; restart redsocks to restore service. Configurations without `user`
continue to run entirely as root.

## Capture TCP connections generated by this Mac

An ordinary inbound `rdr` rule does not capture connections generated locally.
The sample anchor routes the selected user's outbound traffic through `lo0`
and redirects it there. The forwarding process runs as the service user while the anchor captures only
the selected application user, avoiding recapture of its own proxy connections. See also the
[macOS PF routing example in mitmproxy's documentation](https://docs.mitmproxy.org/stable/howto/transparent/).

1. Copy `examples/pf-macos.anchor` to a working file. Set `capture_user` to the
   output of `id -u` for the ordinary application user. Start redsocks with sudo and retain the configured service user;
   do not capture that service UID or UID 0 for general traffic capture.
2. Replace `203.0.113.10` in the bypass table with the real upstream proxy IP.
   If using `ssh -D`, exempt the SSH bastion's IP too: the SSH process normally
   runs as the captured user. Exempt other destinations that must remain direct.
3. Copy the edited anchor to `/etc/pf.anchors/redsocks`. Back up `/etc/pf.conf`,
   retaining its existing Apple rules. Add `rdr-anchor "redsocks"` in its
   translation section, `anchor "redsocks"` in its filter section, and
   `load anchor "redsocks" from "/etc/pf.anchors/redsocks"` alongside its other
   anchor-loading statements. PF requires translation rules before filter rules.
4. Check the whole configuration before loading it:

   ```sh
   sudo pfctl -nf /etc/pf.conf
   sudo pfctl -f /etc/pf.conf
   sudo pfctl -E
   ```

   Retain the enable token printed by `-E`. Loading the main ruleset can replace
   dynamically installed main rules; account for existing VPN or sharing rules.
5. As the captured user, make an IPv4 request without curl's explicit proxy:

   ```sh
   curl -4 --noproxy '*' --max-time 15 https://example.com/
   sudo pfctl -a redsocks -vvs rules
   sudo pfctl -s state
   ```

   Verify redsocks logs the **original remote IP and port**, the upstream proxy
   receives that destination, and data flows both ways. A successful request
   alone does not prove interception: the PF counters and proxy logs must agree.

To stop interception, empty only this anchor, then stop redsocks:

```sh
sudo pfctl -a redsocks -F rules
sudo pfctl -a redsocks -F nat
```

Existing PF states may persist until their connections close. For permanent
removal, remove the three added anchor references and reload the saved ruleset.
Release only your enable reference with `sudo pfctl -X TOKEN`; avoid disabling
PF globally if another service uses it.

## General UDP through utun

Use a SOCKS5 server with **UDP ASSOCIATE** support and a reachable UDP relay.
The application payload travels in UDP between redsocks and that relay.
OpenSSH `ssh -D` supports TCP only; HTTP CONNECT and SOCKS4 cannot serve this
UDP path either. The TCP control connection stays open for each association.

General UDP capture needs the original destination of every datagram. In live
testing, PF redirection did not preserve distinct flows reliably when one
application socket contacted several destinations through a single listener.
The utun mode instead reads the original IPv4/UDP packet and injects replies
with the remote source IP and port. No destination NAT is used for this mode.

1. Edit `examples/redsocks-macos-udp.conf` with your upstream IP, port and
   credentials. Choose an unused interface name, such as `utun100`; check with
   `ifconfig -l`. Redsocks creates the interface and fails if it is already in
   use. This sample handles UDP alone. To use TCP too, copy its `redudp` section
   into your existing TCP configuration instead of running a second daemon.
2. Start redsocks as root:

   ```sh
   sudo ./redsocks -c examples/redsocks-macos-udp.conf
   ```

3. In another terminal, configure the newly created interface before capturing
   traffic:

   ```sh
   sudo ifconfig utun100 inet 198.18.255.1 198.18.255.2 netmask 255.255.255.255 mtu 65535 up
   ```

   These two addresses must be unused on your system; change them consistently
   here and in the anchor if they conflict with an existing network or VPN.
   The large virtual MTU allows ordinary large UDP datagrams to arrive intact.
4. Copy `examples/pf-macos-udp.anchor` to a working file. Set `capture_user` to
   your ordinary application UID, replace the upstream placeholder, and add
   any destinations that should stay direct. Keep the configured service user distinct from `capture_user`. Install
   this as a separate `/etc/pf.anchors/redudp` file. Retaining the existing Apple
   rules, add these lines to `/etc/pf.conf` in its filter and anchor-loading
   sections respectively:

   ```pf
   anchor "redudp"
   load anchor "redudp" from "/etc/pf.anchors/redudp"
   ```

   Syntax-check and load the complete configuration, then enable PF with
   `pfctl -E`, as in the TCP instructions. Retain the enable token. This UDP
   anchor uses `route-to` only; do not redirect its packets to a UDP listener.
5. As the selected application user, exercise a public UDP destination. For
   example:

   ```sh
   dig @1.1.1.1 example.com A
   sudo pfctl -a redudp -vvs rules
   ```

   Confirm the anchor counters, redsocks logs and upstream traffic agree.
   The example bypasses private networks, including typical router DNS
   addresses. Resolver traffic to those addresses remains direct.

To stop capture, run `sudo pfctl -a redudp -F rules` before stopping redsocks.
Closing redsocks removes its utun interface. After a restart, configure the
new interface again before reloading the anchor. For permanent removal, remove
the two added PF references and reload the saved main ruleset; release your PF
enable token as described above. Existing PF states can outlive anchor rules
until their flows expire.

## Fixed-destination UDP through PF

For one target, such as a particular DNS server, no utun interface is needed.
`examples/redsocks-macos-udp-fixed.conf` sends every received datagram to
`1.1.1.1:53` through SOCKS5. Change `dest_ip` and `dest_port` together, and keep
the target synchronized with `examples/pf-macos-udp-fixed.anchor`.

Start that configuration as root, select the ordinary user's UID in the
anchor, and install it using the TCP section's `rdr-anchor`, `anchor`, and
`load anchor` procedure under a separate name such as `redudp-fixed`.
The anchor routes matching traffic through `lo0` and redirects it to
`127.0.0.1:12346`; PF reverses the translation for replies. The upstream still
needs UDP ASSOCIATE support. This mode deliberately forwards to the configured
target, so its rules must match only that target. Use utun when destinations
vary.

## DNS through a TCP-only proxy

`dnsu2t` accepts UDP DNS requests and sends length-prefixed DNS messages over
one reusable TCP connection. This works with `ssh -D` when that TCP connection
is redirected through redsocks. It needs no SOCKS5 UDP support.

Use `examples/redsocks-macos-dns.conf`, pointing its `redsocks` section at your
SOCKS5 upstream. Install a separate PF anchor using the TCP anchor procedure,
with these rules (keep the remote DNS IP/port synchronized with the config):

```pf
rdr pass on lo0 inet proto tcp from any to 1.1.1.1 port 53 -> 127.0.0.1 port 12345
pass out route-to (lo0 127.0.0.1) inet proto tcp from any to 1.1.1.1 port 53 user nobody
```

This narrowly captures the DNS helper's outgoing TCP connection. Start the
example with sudo, then test `dig @127.0.0.1 -p 5353 example.com A`. Ordinary
applications need their resolver configured to use this service; a standalone
resolver on port 53 or a DNS forwarder can supply the normal resolver port.
The original limitation on simultaneous identical DNS transaction IDs remains:
a colliding request is dropped and can be retried by the client.

## Linux parity and throughput

The port provides the original IPv4 TCP proxy protocols and authentication,
SOCKS5 UDP, `dnstc`, `dnsu2t`, daemon/chroot configuration, and privilege dropping.
TCP interception uses PF and arbitrary UDP interception uses utun; Linux keeps
iptables/TPROXY. IPv6 and SOCKS5 UDP fragmentation were not implemented by the
original baseline and are outside this parity target.

macOS uses libevent's buffered TCP pump because Linux `splice(2)` is not
available. `python3 tests/benchmark.py` checks payload integrity and reports
median throughput over three 32 MiB loopback transfers. Linux runs both pumps;
macOS runs the buffered pump. Results are informational, not a promise of
identical throughput across hardware or operating systems. CI records these
measurements alongside functional tests. The DNS relay also uses buffered TCP,
so it handles partial writes without requiring Linux Fast Open.

For the validated parity build, the CI loopback measurements were 45.78 MiB/s
on Intel macOS and 339.82 MiB/s on Apple Silicon macOS. Linux/GCC measured
174.71 MiB/s buffered and 1,728.44 MiB/s with splice. These runners have different
hardware and load, so the figures establish a working data path rather than a
controlled OS comparison. The feature parity claim does not include matching
Linux splice throughput.


## Limits

- Only IPv4 is supported. IPv6 remains outside these interception rules. Only
  the selected user's matching destinations are captured; the examples are not
  a system-wide traffic containment policy.
- UDP is enabled by default on Linux and macOS; `REDUDP=0` disables it. Linux
  retains its existing transparent socket/TPROXY backend. `local_tun` requires
  macOS and cannot be combined with `local_port` or `dest_ip`/`dest_port`.
- The utun backend reassembles IPv4 UDP fragments, including out-of-order
  fragments and identical duplicates. Conflicting overlaps discard the
  assembly. Each interface holds at most 32 incomplete datagrams (about
  2.4 MiB), with a 30-second lifetime; expired entries are reclaimed on the
  next fragment or shutdown. These bounds protect the daemon under packet loss
  or fragment floods. SOCKS5 protocol fragmentation and domain-name/IPv6 relay
  addresses remain unsupported, as in the original IPv4 UDP relay.
- An IPv4 SOCKS5 UDP header adds 10 bytes, limiting application payloads to
  65,497 bytes. Network MTUs and upstream limits may be smaller. macOS UDP
  socket buffers are sized to accommodate full IPv4 datagrams. ICMP errors
  and path MTU discovery are not relayed to the application.
- Both DNS helpers are included by default. `dnstc` encourages clients to
  retry over TCP; `dnsu2t` performs UDP-to-TCP conversion itself. `DNSU2T=0`
  disables the latter. They need explicit resolver/interception configuration.
- The small `pf-darwin.h` declaration matches Apple's private DIOCNATLOOK ABI.
  Compile-time layout checks do not prove kernel compatibility; runtime lookup
  needs verification on each supported macOS release.

## Verification

The release and debug builds and all 15 portable regression tests pass in
GitHub Actions on Intel macOS, Apple Silicon macOS, Linux/GCC and Linux/Clang.
The native Apple Silicon build uses Clang and libevent 2.1.13; the portable
tests also pass under AddressSanitizer and UndefinedBehaviorSanitizer. The
curated fixes branch was tested separately before the macOS changes. Negative
controls confirm that reverting #123 or #100 makes its corresponding
regression test fail.

The PF ABI layout checks compile for both arm64 and x86_64, and the sample
anchor passes `pfctl -n`. GitHub Actions additionally covers Linux/GCC,
Linux/Clang, Intel macOS and Apple Silicon macOS. See the fork's Actions page
for the current commit's results.

Portable macOS checks also exercise fragment validation and bounds and reject
invalid descriptors passed to the PF helper. The privileged interception tests are separate from `make check`:

```sh
sudo python3 tests/macos_pf_test.py
sudo python3 tests/macos_udp_test.py
```

They require the active main ruleset's standard `com.apple/*` filter and rdr
anchor hooks. They create an isolated child anchor matching only
root-originated TCP or UDP to `198.18.0.0/24` ports 18080–18081, start a local
fake SOCKS5 proxy, and verify the destination and bidirectional payloads.
The UDP suite covers PF fixed-target replies, a single socket addressing three
destinations through utun, separate clients, connected sockets, authentication,
and empty and 8 KiB datagrams, including forced IPv4 fragmentation after
dropping privileges. The TCP PF suite also runs with an unprivileged worker. It temporarily creates and configures `utun100`,
which must be unused. The scripts never edit `/etc/pf.conf` or reload the main
ruleset. On exit they remove their own rules and interfaces and release only
their own PF enable references. Like other PF rules, an existing quick rule or
`set skip on lo0` can prevent interception.

Both privileged suites pass on Intel and Apple Silicon macOS CI runners
(macOS 15). The user also confirmed the TCP test's PASS result on the target Apple Silicon
Mac running macOS
26.7.3. The new UDP and privilege-separation paths have not been exercised on that
target Mac yet. These
checks use local SOCKS5 test servers; an external UDP relay and the target
machine's existing firewall/VPN configuration still require their own
validation.
